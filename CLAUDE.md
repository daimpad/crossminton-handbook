# CLAUDE.md

Leitfaden für Beitragende und KI-Assistenten, die an dieser Codebasis arbeiten. Kurz halten, was der Code schon sagt; hier steht nur, was man **wissen muss, bevor** man etwas ändert.

## Was das ist

Clientseitige Lernapp für Crossminton. Rein statisch: HTML/CSS/JS als ES-Module, **kein Build-Schritt, keine Server-Komponente, keine npm-Laufzeitabhängigkeiten**. Inhalte kommen aus JSON in `data/`, Fortschritt lebt in `localStorage`. Maßgeblich ist die Spezifikation in `docs/uebergabe-spezifikation.md` — bei Konflikten gewinnt sie.

## Nicht verhandelbare Architektur

- **Rein clientseitig.** Keine Abhängigkeit, die einen Bundler oder eine Laufzeit voraussetzt. Bibliotheken, wenn überhaupt, als lokal eingecheckte statische Datei (so wie die Schriften).
- **Inhalt getrennt vom Pfad.** Es gibt *einen* Baustein-Pool; die vier Pfade sind Traversierungen darüber (`js/pfade.js`). Inhalt wird nie dupliziert.
- **Identität getrennt von Beschriftung.** Sprachneutrale IDs stehen in der Inhalts-JSON, sichtbare Texte in `data/labels/<sprache>.json`. Nie einen Anzeigetext hart in JS/HTML schreiben — immer `t()`, `label()` oder `text()` aus `js/i18n.js`.
- **Fortschritt ist baustein-gebunden.** Status hängt am Baustein, nie am Pfad (Spez. 7.5). Der Zustandsraum ist erweiterbar: `offen → erledigt` aktiv, `beherrscht` vorgesehen, aber inaktiv — keine Datenmigration bei späterer Aktivierung.
- **Zwei-Ebenen-Logik (Spez. 4.4).** Der Voraussetzungsgraph *sortiert* nur, er *sperrt nie*. Fehlende Voraussetzungen erscheinen als Hinweis, nie als Zugangssperre.

## Wo was liegt

| Ebene | Dateien | Regel |
| --- | --- | --- |
| Daten | `js/daten.js`, `js/graph.js` | reine Funktionen, kein DOM; Indizes + Konsistenzprüfung |
| Engine | `js/pfade.js`, `js/fortschritt.js`, `js/aktionen.js` | reine Funktionen über Daten+Zustand → annotierte Listen; **kein DOM** |
| Zustand | `js/zustand.js` | einziger localStorage-Zugriff, versioniertes Schema |
| i18n | `js/i18n.js` | alle sichtbaren Texte laufen hier durch |
| Ansichten | `js/ansichten/*.js` | rendern HTML-Strings + binden Events; lesen die Engine, mutieren nie direkt |
| Shell | `js/app.js` | Boot, Hash-Router, Menü |

Faustregel: **Logik gehört in die Engine (testbar, DOM-frei), nicht in die Ansichten.** Neue Regeln zuerst in `js/pfade.js`/`js/fortschritt.js`, dann in `tests/engine.test.mjs` absichern.

## Verifikation (Pflicht vor jedem Commit)

```sh
node tests/engine.test.mjs          # Engine gegen die Referenzdaten (dependency-frei)
python3 -m http.server 8000         # dann im Browser durchklicken
```

Für den End-to-End-Durchlauf (Playwright, mobil + Desktop) siehe `.claude/skills/verify/SKILL.md` — dort steht der komplette Fahrplan inkl. der heiklen Stellen (Delta nur im Kompetenz-Kontext, Ampel-Status, Wizard-Ausstieg, Hamburger). **Verifikation heißt: die laufende App beobachten, nicht nur Tests laufen lassen.**

## CI / Design

Farben, Typografie und Icon-Regeln stehen in `docs/ci.md` und sind als CSS-Variablen in `css/app.css` (`:root`) zentralisiert. Verbindlich:

- **Hauptfarbe `#38a4f1` ist Akzent** (Links, Aktion, Aktiv-Zustand), keine Flächenfarbe; **Überschriften ruhen in Tinte** (`--ueberschrift` = `--tinte`), nicht blau.
- **Signalfarben nach Ampellogik**, nie dekorativ: Rot `#f4402a` = offen, Gelb `#f2d93b` = teilweise/Hinweis, Grün `#24bd47` = erledigt (je mit `-text`/`-weich`-Rolle). Werte gelten hell wie dunkel — im Dunkeln nur aufgehellt.
- **Hell & Dunkel über denselben Token-Satz** (`:root` hell; `@media (prefers-color-scheme: dark)` + `:root[data-theme='dunkel']` kippen die Tokens). Weil Ansichten/Komponenten **ausschließlich Tokens** lesen, flippt das ganze Bild automatisch — Farben nie hart schreiben. Umschalter im **Profil-Selektor UND im Hamburger-Menü** („Darstellung": auto/hell/dunkel, `einstellungen.thema`; **Standard ist `hell`** — nur die ausdrückliche Wahl `auto` folgt dem OS via `prefers-color-scheme`) setzt `data-theme` auf `<html>`; das **Inline-Skript im `<head>`** setzt es flackerfrei vor dem ersten Anstrich (ohne gespeicherte Wahl → `hell`), `wendeThemaAn()` (`js/oberflaeche.js`) zur Laufzeit — beide halten `theme-color` nach. Hauptfarbe & Ampel bleiben in beiden Schemata verbindlich.
- **Icons immer farbig, nie schwarz** (Font Awesome Solid, lokal). Neue Icons: eine Codepoint-Zeile in `css/schriften.css`; Baustein-Icons in `js/oberflaeche.js` (`BAUSTEIN_ICONS`).
- **Container-Radius 14px** (gestuft: `--radius`/`--radius-gross` 20px/`--radius-klein` 9px), **weiche mehrlagige Elevation** (`--schatten-karte` dauerhaft, kein dominanter 1px-Rahmen), Hover-Schatten nur auf Zeigergeräten, `prefers-reduced-motion` respektieren.

- **Nach Datenänderung Skelette neu erzeugen:** `data/labels/{en,fr,pl}.json` sind strukturgleiche Gerüste von `de.json`; beim Hinzufügen neuer de-Schlüssel die Skelette regenerieren (leere Werte fallen zur Laufzeit auf de zurück).

Programmatische Navigation läuft nie über `location.hash = …`, sondern über `geheZu(ziel)` aus `js/oberflaeche.js` (Ereignis `app:gehe-zu`, damit Ansichten den Router nicht importieren müssen — dasselbe Muster wie `neuRendern()`). **`WURZEL`** (`js/app.js`, exportiert) ist der Montagepunkt und kommt aus `document.baseURI`, **nicht** aus `import.meta.url` — das Dokument kann unter einer verschachtelten Route ausgeliefert werden (404-Umweg oder SW-Cache), und nur das `<base>`-Element bleibt dabei korrekt. **`<base href>` ist damit doch nötig**, entgegen der früheren „läuft ohne `<base>`-Tag" Architekturregel: ein Inline-Skript ganz oben in `index.html` (nach `meta charset`, das aus Spez.-Gründen in den ersten 1024 Byte stehen muss) korrigiert `<base>` synchron auf den echten Montagepunkt, bevor irgendein anderes `<link>`/`<script>` geparst wird. Derselbe Präfix-Wert steht doppelt (`index.html` + `404.html`, dort als `PRAEFIX`-Variable) — der einzige deploy-abhängige Wert im ganzen Mechanismus; **produktiv steht er auf `''`** (Custom Domain `crossminton-handbook.de`, Montage an der Wurzel, s. den Domain-Fallstrick unten), der Unterpfad-Zweig bleibt als Code-Pfad für einen möglichen künftigen github.io-Fallback erhalten. **Der Modul-Graph wird jetzt per JS vorgeladen**, nicht mehr über statische `<link rel=modulepreload>`: Chromiums Preload-Scanner läse sonst den `<base>`-Platzhalter statt des korrigierten Werts und würde unter Unterpfad-Deploy bei jedem Aufruf falsch anfragen — das Inline-Skript fügt dieselbe Liste per `document.createElement('link')` mit bereits korrekter absoluter URL ein. Ein kleiner Rest bleibt bewusst bestehen (die paar echten statischen Tags — beide CSS-Dateien, `js/app.js`, das Kopf-Logo — lösen aus demselben Grund unter Unterpfad-Deploy beim Preload-Scanner falsch auf, sichtbar als eine Handvoll harmloser 404-Konsoleneinträge; der eigentliche Parser lädt sie Sekundenbruchteile später korrekt, die Seite rendert und funktioniert vollständig richtig — lokal an der Wurzel bleibt die Konsole sauber). **`404.html`** ist der etablierte SPA-Fallback (rafgraph/spa-github-pages): GitHub Pages liefert für `/baustein/griff` einen 404, weil keine Datei existiert; die Datei kodiert die Route in `?/…` und leitet zur Wurzel um, das Gegenstück-Skript in `index.html` schreibt sie vor dem Boot in die History zurück. **`sw.js`s `bedieneNavigation`** verwirft eine 404-Serverantwort und liefert die gecachte Hülle aus (sonst sähe der Nutzer die Umleitungsseite statt der App) — nur wenn auch die Hülle fehlt, gewinnt die 404-Antwort. Geteilte Alt-Links (`#/…`, aus der Zeit vor Tier 2 oder aus `teileLink()`) werden beim Boot einmalig umgeschrieben, bevor `rendern()` läuft — sie tragen weiter. `CACHE` in `sw.js` auf v35 (404.html neu in der SHELL). **Der globale Klick-Interceptor erkennt rohes `href="#/…"` zusätzlich zu bereits normalisierten Pfaden:** zwei Ansichten (`suche.js`, `ko-turnier.js`) patchen ihren Ergebnis-/Setup-Bereich lokal statt über den globalen `rendern()`-Zyklus (Suche hält so den Eingabe-Fokus, KO-Turnier den Entwurf) — `normalisiereLinks()` sieht deren frisch eingefügte Links nie, sie tragen also weiter rohes `#/…`. `new URL('#/x', …)` würde das als reines Fragment lesen (Pfad bliebe unverändert, der Klick liefe ins Leere); der Interceptor prüft daher `href.startsWith('#/')` **vor** der URL-Auflösung und ruft in dem Fall direkt `navigiere()`. Reine Fragment-Links wie der Skip-Link (`href="#ansicht"`, kein Slash danach) bleiben davon unberührt und laufen weiter über die normale URL-Auflösung (dort No-op, weil der Pfad unverändert bleibt — die eigentliche Fokus-Logik sitzt in einem eigenen, unabhängigen Klick-Handler).
- **Titel/Beschreibung/Canonical sind je Route eigenständig — eine Zuordnung, zwei Verbraucher (SEO Tier 2, Baustein 2).** `js/seo.js` (`seiteMeta(daten, segmente)`, rein/DOM-frei) leitet `{titel, beschreibung}` aus genau den Funktionen/Labels ab, die die jeweilige Ansicht schon für ihre eigene Überschrift nutzt (`kompetenzpfad`/`themenDomaenen`/etc. aus `js/pfade.js`, `bausteinText()`+`ausschnitt()` aus `js/suche.js` für die Baustein-Beschreibung, `app-info.json` für Über/Mitmachen/Impressum/Datenschutz) — **keine zweite, gepflegte Text-Zuordnung**. Zwei Verbraucher: **`js/app.js`** ruft `seiteMeta()` bei jedem `rendern()` auf und setzt `document.title` + `<meta name="description">` + `<link rel="canonical">` (Wert `window.location.origin + pathname`) live im Client — ohne das bliebe der Tab-Titel nach einer SPA-Navigation für immer generisch. **`scripts/prerender.mjs`** liest denselben, vom Client bereits gesetzten Wert nur aus dem DOM aus, rechnet nichts zweimal. **Die Startseite ist die eine Ausnahme:** Sie behält ihren handgepflegten Tier-1-Kopf aus `index.html` (reichhaltige OG-Beschreibung + Produktions-Canonical) unangetastet — `js/app.js` sichert die drei Original-Werte einmalig als `urspruenglicherKopf` beim Modul-Load (bevor irgendein `rendern()`-Lauf sie anfassen könnte) und stellt sie bei **jeder** Rückkehr zu `/` wieder her (nicht nur beim ersten Laden — sonst bliebe nach einem Ausflug auf eine andere Route eine falsche Beschreibung hängen); `scripts/prerender.mjs`s `baueSnapshot()` überspringt `pfad === '/'` aus demselben Grund. Ein Playwright-Rauchtest deckte das Problem ursprünglich auf (Titel/Beschreibung vor und nach einem Routenausflug verglichen) — ohne die Ausnahme hätte der erste Client-Boot die Tier-1-Beschreibung sofort überschrieben.
- **`scripts/prerender.mjs` erzeugt beim Deploy statische Snapshots je Route + die volle `sitemap.xml` (SEO Tier 2, Baustein 2) — läuft NUR im Workflow, nie lokal/buildfrei nötig.** Bootet die App **einmal** in einem echten Playwright-Tab (`ladeDaten()`), leitet daraus per `page.evaluate()` die Routenliste ab (dieselben reinen Funktionen aus `js/daten.js`/`js/pfade.js` — keine zweite, gepflegte Liste: `kompetenzpfad`-Stufen + `trainer`, `themenDomaenen`, `spielformen`, `witterungen`/`untergruende`, alle `daten.einheiten`, alle `daten.bausteine`, plus die statischen Reiter) und durchläuft sie per **In-Page-SPA-Navigation** (`history.pushState` + `popstate`-Dispatch — derselbe Weg, den auch ein Klick nimmt), NICHT per 149 einzelnen `page.goto()`-Aufrufen (schneller, ein einziger `ladeDaten()`-Lauf, keine Divergenz zwischen Skript- und Laufzeit-Routenliste). Je Route wird `document.title`/`meta[name=description]`/`#ansicht`-Inhalt aus dem DOM gelesen (von `js/seo.js` bereits gesetzt, s. o.) und in eine Kopie der `index.html`-Vorlage montiert (`<title>`/`description`/`canonical`/`og:*`/`twitter:*` per Regex ersetzt, `#ansicht`-Inhalt eingefügt) — außer für `/`, das unverändert bleibt. **Prerender-würdig ist, was ohne persönlichen Zustand eine echte Seite ergibt** (Zwei-Ebenen-Logik: nichts gesperrt) — bewusst ausgeschlossen: `/onboarding`, `/pfad/individual`, `/plan`, `/suche`, `/profil`, `/merkliste`, `/ko-turnier` (zeigen ohne `localStorage` nur ein leeres Formular/eine interaktive Ansicht). **Staging-Kopie `_site`** liegt unter dem Repo-Root — Node verweigert ein rekursives `cp()` in die eigene Unterverzeichnis, darum kopiert `kopiere()` **Eintrag für Eintrag** (`readdirSync` + `cpSync` je Top-Level-Datei/-Ordner, `.git`/`node_modules`/`_site` ausgenommen) statt eines einzigen `cpSync(REPO, ZIEL, {recursive:true})`. Server für den Tab: `python3 -m http.server --directory _site` als Kindprozess (dieselbe Server-Wahl wie überall sonst im Projekt). **Playwright ist eine reine CI-Werkzeug-Abhängigkeit** (`deploy`-Job in `deploy-pages.yml`: `npm install --no-save playwright@1.56.1` + `npx playwright install --with-deps chromium`) — **kein `package.json` im Repo**, `node_modules`/`_site` sind gitignored, lokale Entwicklung bleibt vollständig buildfrei über `python3 -m http.server`. Ergebnis: **149 Routen** (108 Bausteine, alle Pfad-Achsen, 8 Trainingseinheiten, Regeln/Turnier/Ausrüstung/Über/Mitmachen/Impressum/Datenschutz + Wurzel), `upload-pages-artifact`s `path` zeigt jetzt auf `_site` statt `.`. **Der Prerender liefert unter dem PRODUKTIONS-Präfix aus, nicht unter `/`** (`praefixSymlink()` legt im Staging einen Selbst-Symlink namens `crossminton-handbook` an, `PRAEFIX` wird aus `SITE_URL` abgeleitet — kein weiterer deploy-abhängiger Wert; der Symlink wird nach dem Erfassen entfernt und darf nie ins Artefakt): sonst backt `normalisiereLinks()` wurzel-relative Links (`/pfad/themen`) ein, die ausgeliefert **neben** die App zeigen — genau das brach die Seite nach dem ersten Baustein-2-Deploy flächig mit echten 404ern. Modul-Importe in `page.evaluate` laufen darum über `new URL(name, document.baseURI)`, nie wurzel-absolut. **`pruefeLinks()` ist das Gegenmittel:** es prüft jeden Schnappschuss darauf, dass kein `<a href>` wurzel-absolut aus dem Montagepunkt fällt, und **bricht mit Exit-Code 1 ab** (CI schlägt fehl, statt Kaputtes auszurollen). Merkregel für alles Pfad-Bauende: **unter simuliertem Unterpfad verifizieren, nicht nur unter `/`** — bei Wurzel-Montage sind beide Fehler dieser Klasse ein No-op und bleiben unsichtbar. **Seit dem Umzug auf die Custom Domain ist `SITE_URL` `https://crossminton-handbook.de` (kein Unterpfad mehr), `PRAEFIX` leitet sich daraus als `''` ab — `praefixSymlink()`/`pruefeLinks()` sind dadurch im aktuellen Deploy faktisch No-ops**, bleiben aber unverändert im Code, falls die App je wieder unter einem Unterpfad läuft (z. B. github.io als Fallback).
- **Werte aus der URL sind ungeprüfte Eingabe — sie müssen kodiert UND escaped werden.** `?kontext=` ist der einzige URL-Parameter, den eine Ansicht weiterverarbeitet (`js/ansichten/baustein.js`, `kontextZuListe()` → `href` der Fußnavigation „Zur Liste"). Er trug ein **reflektiertes XSS**: `kontextZuListe` setzte das Segment hinter dem `:` roh in einen Pfad, und die Fußnav setzte das Ergebnis roh ins `href` — ein teilbarer Link wie `/baustein/griff?kontext=x:"><img src=y onerror=…>` führte beliebiges JS in der App-Origin aus, auch über den **404-Umweg der Produktion** (`/?/baustein/griff&kontext=…`). Behoben an beiden Enden: `encodeURIComponent()` an der Quelle (der Wert wird ein URL-Pfadsegment) **und** `esc()` an der Senke. Regel für neue Ansichten: **jedes** `${…}` in einem Attribut läuft durch `esc()`, ohne Ausnahme — alle Nachbar-`href` in derselben Vorlage taten es bereits, die eine Lücke fiel dadurch nicht auf. `esc()` deckt `& < > "` ab, was für doppelt-quotierte Attribute reicht (im ganzen Ansichts-Layer gibt es kein einfach-quotiertes Attribut); für URL-Segmente ist `encodeURIComponent()` zusätzlich richtig, nicht alternativ.
- **`zuUrl()` in `js/app.js` ist IDEMPOTENT — ein bereits montagepunkt-absoluter Pfad wird nicht erneut mit `WURZEL` versehen.** Der globale Klick-Interceptor reicht `url.pathname` herein, und der trägt den Montagepunkt schon (die DOM-Links sind nach `normalisiereLinks()` bzw. im Prerender-Schnappschuss absolut). Ohne die `startsWith(WURZEL)`-Prüfung entstand unter Unterpfad-Deploy `/crossminton-handbook/crossminton-handbook/…`; der Router deutete das als unbekannte Route und rendert die Startseite — sichtbar als **„Klick tut nichts, ich bleibe auf derselben Seite"**. Lokal an der Wurzel (`WURZEL === '/'`) ist das Verdoppeln ein No-op, darum fiel es dort nie auf. Wer `zuUrl`/`navigiere`/`geheZu` anfasst: beide Eingabeformen (`#/x` **und** `/<wurzel>/x`) müssen dasselbe Ziel ergeben.
- **Produktion läuft unter der Custom Domain `crossminton-handbook.de`, nicht mehr unter `daimpad.github.io/crossminton-handbook/`.** Repo-seitig sind das alle Stellen, an denen der Montagepunkt/die absolute URL deploy-abhängig ist: `PRAEFIX` in `index.html` + `404.html` steht jetzt auf `''` (Wurzel-Montage), `SITE_URL` in `scripts/prerender.mjs` auf `https://crossminton-handbook.de` (leitet `PRAEFIX` automatisch mit ab, s. den Prerender-Fallstrick oben), Canonical/OG/Twitter/JSON-LD in `index.html`, `robots.txt`s `Sitemap:`-Zeile und die eingecheckte `sitemap.xml` zeigen alle auf die neue Domain. Eine neue Datei **`CNAME`** im Repo-Root (Inhalt: `crossminton-handbook.de`) sagt GitHub Pages die Custom Domain an — `scripts/prerender.mjs`s `kopiere()` nimmt sie automatisch mit ins `_site`-Artefakt (sie ist kein `AUSSCHLUSS`-Eintrag). **Zwei Schritte bleiben zwingend außerhalb des Repos** (nicht automatisierbar): (1) im GitHub-Repo unter Settings → Pages → „Custom domain" `crossminton-handbook.de` eintragen (das ist eine Repo-Einstellung, kein API-Tool in diesem Environment kann das setzen) und nach DNS-Propagation „Enforce HTTPS" aktivieren; (2) beim Domain-Registrar/DNS-Anbieter die Records auf GitHub Pages zeigen lassen (bei der nackten Domain vier `A`-Records auf GitHubs IPs + optional `AAAA` für IPv6, bei einer Subdomain ein `CNAME`-Record auf `<user>.github.io`) — Details in GitHubs eigener Doku „Managing a custom domain for your GitHub Pages site". Ohne diese beiden externen Schritte bleibt die App unter `daimpad.github.io/crossminton-handbook/` erreichbar, auch wenn alle Repo-Werte schon auf die neue Domain zeigen.
- **Genau eine `<h1>` je Ansicht — im Onboarding ist es die Schritt-Frage.** `renderOnboarding` rendert `inhalt.frage` als `<h1>` auf **jedem** Schritt (früher `<h2>`, und die `<h1>` hing an Schritt 0 → Schritte 2–5 hatten gar keine H1); der Willkommens-Titel steht auf Schritt 1 als `<p class="onboarding-willkommen">`-Lead. `heroKlein`/`markeHeroGross` liefern sonst die H1 — eine View gibt nie zwei H1 aus.
- **CTA-Pfeile laufen über die aria-hidden FA-Komponente, nie als literales `→`/`←` im Text** (Screenreader würden das Glyph vorlesen). `<i class="fa-solid fa-arrow-right" aria-hidden="true">` ist der Standard; **`fa-arrow-left` ist NICHT im FA-Subset** (rendert als Tofu) — der „vorherige"-Link der Baustein-Fußnav nutzt daher `<span aria-hidden="true">←</span>`. Die Fußnav trägt ein `aria-label` (`baustein_navigation`). CTA-Sprache ist sonst konsistent (Objekt + Infinitiv, du-Form): das Quittier-Label heißt „Als mitgenommen abhaken" (Familie mit „Als gelesen/erledigt abhaken").
